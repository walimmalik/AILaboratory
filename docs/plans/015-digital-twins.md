## What this plan delivers

A digital twin for **every instrument in the lab** (Wali, 2026-09-30), bound to the instrument registry:

- **The twins themselves**, taken from echo650-twin: each instrument's definition (parts, motions, commands and their preconditions), its behaviour engine (state, timing, what happens to plates and liquids), its 3D model, and for the FlexPod the workcell layout, robot reach and move times.
- **Binding to the registry:** an instrument kind names its twin; a registered instrument's current configuration (Flex modules, STAR carriers, FeliX head) becomes the twin's configuration; a workcell's members are checked against the devices in its twin workcell, both ways.
- **Simulation as an operation:** "how long does this transfer plan take on Echo 1", "run this instrument session on the twin and show me", available to people and agents alike, with every time marked simulated and its source shown.
- **3D views** on the instrument page, the workcell page and later the schedule playback (019d).
- **Calibration hooks:** the twins' timing parameters are the ones 019's timing models calibrate from real logs (S13), so a calibrated twin says "predicts Echo runs within ±4%, from 23 runs".

## Starting point: echo650-twin

Read at commit 59a7a6a. Full survey in the coverage file; the parts that shape this plan:

- **Twins are headless.** `TwinEngine` (`src/engine.js`) has no Three.js: `loadDefinition`, `check(command)`, `execute(command, params)`, `tick(dt)`, `snapshot()`, `reset()`, events per command and phase. Every device engine extends it. So twins can run in the API process (for durations and checks) and in the browser (for 3D) from the same code.
- **One definition contract,** `lab-twin/0.2` (`src/domain/definition.js`): components, motion bindings, commands with `requires`, `sources`, `assumptions`, `fidelity`. Imported meshes carry the same manifest in `extras.labTwin`.
- **A capability wrapper and one clock** (`src/workcell-v2/native-registry.js`, `runtime.js`): each engine becomes an instance with providers (`native.execute`, or `plate.move` for robots), sites, resources and access contracts; one runtime ticks them all.
- **Workcells are data:** `lab-twin-workcell-package` JSON (tables, equipment poses, reach profiles, access contracts, handoff nests), authored in the twin's studio and saved as files (`packages/saved-workcells`).
- **Timing provenance:** definitions cite manual pages where they can; defaults are "estimated simulation timings, not hardware calibrated"; an overlay (`lab-action-timing/1`) holds calibrated overrides per action with their source.
- **Rendering:** `TwinViewer` (`src/viewer.js`) takes a container element and renders on the host's frame loop; wrapping it in a React component is moderate work. The faceplate panels are imperative DOM that call engines directly.
- **Coverage:** full twins for the Flex, Echo 650, STAR, MANTIS, PreciseDrop II, A4S, XPeel and FlexPod (with PlateOrient, LidValet and stackers); thin mesh-plus-one-action twins for the MicroSpin, BlueWasher and Cytomat; none yet for the Vantage, Spark Cyto, FeliX, qTOWER3 and PTC Tempo.
- **Its rule:** "port existing digital twins directly: preserve geometry, assets, articulation, semantic bindings and recognizable motion. Do not rebuild them."

## Proposed model (to be settled by the questions)

| Instance | Twin workcell (T4) | The echo650-twin workcell package for a workcell, versioned |
| State | Simulation run (`sim_`) | One simulation: what was simulated (a transfer plan session, a workflow segment), the twin versions, the timeline of commands and phases, totals, warnings; derived, never edited |
| State | Timing calibration | 019's timing model (`tmm_`) applied as the twin's timing overlay |

## Round 2 questions: the twin standard

From the review of how the existing twins are built (`/mnt/project-files/twins/twin-review.md`) and the draft standard ([015-twin-package-standard.md](015-twin-package-standard.md)). In short, the twins share a skeleton but no standard. Timing is defined in nine different ways, mostly as numbers hard-coded in engines. No time has min, typical and max, or provenance per value. There is no shared command vocabulary, robots' access is written centrally per device, and every new twin needs edits to about six tables of code. None could be uploaded as a file today.

## Round 2 answers

Wali, 2026-10-01:

- **T7 to T12: A.** On T7 Wali asked why "data only" meant no 3D twin. It doesn't: every package carries its 3D model (`model.glb`). "Data only" means there is no runnable code in a package; behaviour that needs code comes from the app's tested templates.
- **T13:** Codex (Astra), which built the twins, gets a plan and audit task for echo650-twin, with the review included: verify the review, audit every twin against the standard, then (in small PRs there) add the schema and checker, move all timing into typed models, map commands to capabilities, give twins their sites and access poses, and export every lab twin as a standard package. Then the packages are uploaded into this app. The task is `/mnt/project-files/twins/codex-astra-prompt.md`.

## Defaults I'm assuming (say if any is wrong)

- **Faceplate panels are not ported.** Controlling a twin by hand from the page goes through operations (rule 2, human = agent), with a plain lab-language form, not echo650-twin's imperative panels. The 3D viewer is wrapped in a React component and follows the bench console tokens (day and night).
- **The FlexPod's workcell runtime** (transport routing, reach, move times, the one-clock runtime) comes in with the twins in 015; the scheduling kernels (action-resource kernel, pending re-planner, exposure kernel) come in with 019 as 000 planned.
- **3D assets:** only the models of instruments the lab has are copied (the imported equipment mesh file is 37 MB, the WellJet model 17 MB, and the lab has no WellJet). Large model files go in Git LFS or are fetched by the sync command rather than committed in plain git; decided in the build step.
- **Everything simulated is labelled simulated,** with the twin version and its fidelity note, until 019's timing models calibrate it from logs; calibrated values show the logs and the held-out error. No claim of physical accuracy that hasn't been checked (rule 10).
- **Twin commands and the device gateway (022) share the capability contract** from 008 (I5), so a transfer plan runs on the twin and later on the real Echo through the same call.
- **Lab memory:** simulation runs are derived data, not outcome data, so 015 ships no detectors; the gap between simulated and measured time is 019e's detector.
