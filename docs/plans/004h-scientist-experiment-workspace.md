## 1. Delivery goal

A scientist can start/resume an experiment, select materials at scale, review the assay-specific design and plate maps, configure supported liquid additions and download the correct worklists without leaving the experiment. The assistant can draft the same objects, resolve the same selections, calculate through the same tools and request the same supported views. Both paths expose unknowns and scope correctly.

This delivers a scientist workspace over the existing lab system. It does not create a generic workflow product or claim to run an instrument. UI navigation is not a scientific state machine. Design acceptance, transfer acceptance, export, simulation and observed execution remain distinct.

## 4. Contract checklist before producers are released

The shared contracts are [C1–C5 in the spec](../specs/experiment-workspace.md#6-proposed-model-changes-and-contracts). A producer is ready only with these concrete examples and checks:

- **C1 workspace/selection:** valid saved context, wrong-lab references, stale selection, all-matches snapshot with exclusions, exact membership receipt, bounded pages and existing-draft completion. The UI and external agent must not depend on a privately held browser list.
- **C2 scientific inputs:** compound target; ELISA kit/target/dilution/standards; cell target/independent seeding volume; optional vs deferred vs required; unsupported type; agent assumption evidence. Experiment replicate/control edits survive reload/recalculation through explicit typed ownership and precedence (A16), without modifying reusable definitions. No formula or requirement rule in ad hoc UI metadata.
- **C3 preparation:** dosing+vehicle+base addition coverage, explicit unavailable addition, unequal source quantities, multiple tubes, 200 destinations plus source/intermediate partitions, control exclusions, row identity, joint reservations and replacement lineage. Candidate creation leaves accepted demand intact; replacement switches the complete scope atomically; rejection/interruption/concurrent replacement and mixed-generation export are covered by A17. Show endpoint composition or why it cannot be calculated.
- **C3 intermediate dilutions:** mixed direct/intermediate dose-response points, preparation stock/diluent sources and devices, target versus achieved concentrations, finite-volume/dead-volume checks and explicit unreachable points. A18 covers the chosen batch-local/shared strategy, preparation-before-use dependencies, dose/solvent changes and UI/agent parity; a planned intermediate is never presented as physically prepared inventory.
- **C4 device setup:** actual registry examples for Echo, Mantis and PDII; source family, installed equipment, connection/loading identity, units and verification. Where evidence is unavailable, stop that device claim and finish independent supported work.
- **C5 review/outputs:** displayed vs actual confirmation scope, changed expected versions, duplicate export bytes from different versions/groups, partial export failure, stale dependency and persisted download after reload. No file-origin inference as a substitute for an export association.

Do not introduce blanket bulk confirmation, a global UI task engine, hard reservations or a new execution state machine to simplify a screen. Use existing people-only confirmation, proposals, evidence and record service boundaries. Scoped readiness projections can improve clarity without changing authority.

## 5. Validation and completion

Source review and prototype browser evidence guide this plan; they do not satisfy runtime acceptance. Implementation PRs record exact SHA, performed checks and unrun checks in their descriptions, with no per-ticket verification documents in the repository.

Required evidence per changed slice:

1. Schema-first definitions and generated outputs; operation valid/invalid/permission cases; calculator tests for scientific invariants rather than mirror tests; cross-module contract tests where affected.
2. A person completes the changed path through usable UI controls. An agent completes the same scientific changes via operations/MCP with the same fixture. Compare scientific values, coverage, provenance/acceptance boundaries and durable receipts; actors may differ.
3. Changed-route browser checks for reload, back navigation, unsaved edits, bounded search, keyboard/focus, contextual details, and exact saved results. Apply the `ui-workflow-fidelity` skill once the integrated UI is usable.
4. Independent review proportionate to scientific/shared-contract risk. Resolve material findings before dependent work or final acceptance; do not treat model agreement as proof.
5. Repository-required `pnpm generate` consistency and `pnpm check` when integration is ready; affected E2E against a bootstrapped disposable lab. Python checks and simulator checks when the science/export path changes. Run full gates once per valid integration revision; repeat only invalidated gates. No new hardware tests.

Scale fixtures must cover (a) 5,000 selected compounds in a larger searchable catalog and (b) 200 destination plates plus actual source/intermediate containers, with enough rows to exercise partitioning. Record workload, bounded page payloads, response/browser timing and memory against the spec's proposed targets; synthetic fixture sizes are not scientific values for real experiments. Performance targets need measured evidence before marketing the capacity.

Completion means the claimed assay journeys pass their applicable spec scenarios using real schemas/operations, supporting records remain contextual, worklists survive chat/navigation/reload, and unsupported physical capabilities remain honestly labeled. The full three-assay plan is not complete after the first compound slice.

### 5.1 Browser and live-agent acceptance for every delivery

Each usable delivery sequence requires a separate browser-capable verification agent, with the primary owning the shared disposable test lab and final conclusion. Use Sol 6.1 for bounded browser checks and Astra where the verification requires cross-module scientific judgment; do not count the implementing agent as its own independent verifier. Apply `ui-workflow-fidelity` against the running implementation and agreed screen behavior.

Verify both paths: (1) the verifier operates the scientist-facing controls, and (2) a real configured assistant receives a natural-language task, calls the actual operations and produces a persisted result visible in the browser. Deterministic tests remain necessary but canned assistant replies, mocked tool calls and the HTML mockup are not live-agent acceptance. Record the actual model/provider used rather than assuming it matches the coding agent. Test people-only confirmation through the disposable lab's scientist test actor; the application assistant must retain its own permissions and stop at its confirmation boundary.
