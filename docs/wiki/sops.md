# SOPs and the library

Two records, two plans: the **library document** is the source as published (011), and the **digital SOP** is the structured, computable procedure built from it (012). Both locked. 011a is built: the file store ([ADR 0033](../decisions/0033-file-store.md)), documents, folder import and the seed loader ([library.md](../architecture/library.md)).

## SOP and literature library (plan 011)

[Plan 011](../plans/011-sop-library.md). The lab's reading shelf, searchable by people and agents.

Open **Library** to **Draft a method**, **Find instructions** or **Find a lab convention**. Drafting starts a new assistant conversation about what the method should achieve and any protocol you have, before creating a draft or assuming settings. The find actions open Documents and Lab memory. **Browse the library** expands the specialist collections and their waiting draft counts; their existing links and filters remain available. **Start here** returns from a specialist collection to these tasks.

Document text results open the source at the matching section of its current parsed text. Back
and reload retain the submitted search, search mode and separate title/status filters. An
unavailable section is explained rather than replaced by the first section; choose another
section or search again. These links do not pin an immutable source edition.

The library API now retains immutable converted-text snapshots. Parse/read/search results carry
an exact source reference, and `library.read {source}` verifies the historical record version,
file membership, stored byte digest and snapshot before reading it. New revisions and improved
conversion leave old snapshots readable; empty sections are retained for new parses. Pre-snapshot
data preserves only observable retained text/headings, with missing old empty headings labeled.
Documents search now links each hit to a read-only exact source reader: copied links and section
navigation preserve its version, file and text snapshot, including historical warnings. Unavailable
attachments remain explicitly unchecked. The SOP source/citation consumer and scientist
selection/adoption UI remain pending; current SOP citations still use their existing contracts.
Asking from the reader carries the open source's exact reference and selected passage or section.
The server verifies that selection before accepting the ask, and chat retains a historical reference
on each message even after navigating elsewhere. Missing or inaccessible source text is not replaced
with current instructions. This identifies the saved source being discussed; it does not validate
its science, adopt it into an SOP, or grant approval or confirmation authority. Older SOP source
associations are not inferred or rewritten.
See [library architecture](../architecture/library.md#exact-instruction-references-library-producer-004g--sg-18).

- **Documents** (built, `DOC-0001`): SOPs, vendor manuals, papers, robot protocol code and web pages, one record per source with its files (original, alternates, supplements); a new revision is a new version and keeps the old file. Folders import from a `manifest.json` or Markdown with front matter (`library:import`); the seed loads `seed/sops/own` and `docs/sop-library`. Each carries its license and a share policy. All Rights Reserved and non-commercial items are lab-private and never go into `seed/` or exports. Evidence names document attributes that have values; the published title (`label`) is record metadata, not an evidence key.
- **File store** (built, [ADR 0033](../decisions/0033-file-store.md)): content-addressed (bytes named by sha256) on a Docker volume, behind an interface that can move to S3-compatible storage on the cluster. Each file is a `fil_` record (`FIL-0001`); the same bytes are stored once; `files.upload` and `files.get` for agents, `/api/v1/files/<id>` for people. A file record is only ever made by `files.upload`, which proves the caller holds the bytes; `records.create` refuses the kind ([library.md](../architecture/library.md)). SDS and CoA files use it too.
- **Parsing** (Markdown, HTML, code and text built, [ADR 0034](../decisions/0034-library-text-and-search.md); PDF and DOCX next): Docling in the science service keeps headings, page numbers, reading order and tables, with OCR for scans. It runs locally, so private manuals never leave the machine.
- **Search** (keyword search built: `library.search`, `library.read`; meaning-based next): hybrid Postgres full text plus pgvector over passages; every hit points to its page and heading. Embeddings are local by default; an OpenAI-compatible provider is optional (and sends text off the machine). One model per lab; switching re-embeds.
- **Mining** (built, [ADR 0035](../decisions/0035-library-mentions.md): `library.mine` matches registry names and catalog numbers, agents add the assay and parameters with `library.propose_mentions`): an agent proposes what each passage mentions (products, labware, instruments, cell lines, assay type) and the parameters it states, linked to registry records. A person confirms in bulk. Record pages gain "Mentioned in".
- **Test set**: `docs/sop-library` has 12 openly licensed SOPs, 7 papers and 4 code items, deliberately including messy SOPs (OpenWetWare), a 73-step ELISA, robot code, and the iGEM InterLab protocol in four forms as ground truth for 012. `seed/sops/own/` has 11 short lab SOPs with variables.
- **Seed refresh**: seed-owned variables and steps refresh only before the SOP's first confirmation. Confirmed history stays pinned; the seed reports that a separate method draft is needed and leaves dependent template refreshes waiting. The working revision operation is future SG-10c work; the seed continues loading independent records.

## Digital SOPs (plan 012)

The [bounded paired backend](../architecture/sops.md#draft-volume-default-decision-preparation-and-apply) prepares one uncited positive same-unit volume default on a never-confirmed draft with exact checks, dependencies and the full Values section review scope. Preparation returns a pending proposal and pauses assistant mutations. People-only Apply requires the shown preview digest; changed meaning stays pending for another click, while success has a durable receipt and leaves the SOP draft with unrelated questions open. People inspect the persisted preview and Apply or Reject it in the shared chat/Review card; final SOP confirmation stays separate. This does not resolve scientific questions or validate the method.

[Plan 012](../plans/012-digital-sops.md). An SOP as a structured, versioned design document. The record (`SOP-0001`, [ADR 0037](../decisions/0037-sop-record.md)) and formulas are built; see [sops.md](../architecture/sops.md).

- **Sections**: overview, materials, solutions, variables, procedure, layout requirements, analysis, timing rules. Our own schema; LabOP is an import path and a benchmark reference.
- **Steps** are typed actions from a fixed vocabulary aligned with instrument capabilities (add, transfer, serial dilute, mix, wash, incubate, shake, spin, seal, peel, read, image, wait, make solution) plus "manual". Steps group and repeat, keep the source wording, and state inputs and outputs so workflows (018) can chain SOPs.
- **Roles, not hard links**: "coating plate: 96-well high-binding, default Thermo 442404". Roles bind to a labware type, lot or instrument when an experiment is planned; until then the default shows as estimated (built: `sops.calculate` with bindings reads a lot's certificate value or a plate's dead volume).
- **Variables**: inputs per run (samples, replicates), defaults, values read from records (a plate's dead volume on the pipetting instrument, a lot's CoA concentration) and computed values in a small expression language with units and exact decimals: `n_samples * replicates * well_volume + dead_volume` (built: `sops.evaluate`, [ADR 0036](../decisions/0036-sop-expressions.md)).
- **Timing windows** are typed constraints ("read within 30 min of stop") with a source, and bind the scheduler.
- **Variants**: scale and format are variables; a structural change is a derived SOP that shows its diff to the parent. No nesting; composition belongs to templates and workflows.
- **Digitizer**: an agent turns a library document into a draft, citing the passage behind every step and value, and records open questions where the source is unclear. A reviewer model then checks it (two rounds by default), fixes only what the source settles as tracked changes, and asks where it is ambiguous. A person confirms the SOP once, and each part keeps its own confirmation (built: open questions that only a person answers, `sops.answer_question`, `sops.check_citations`, which checks every quote against its passage, and the review cycle `sops.review`, [ADR 0038](../decisions/0038-sop-review-cycle.md)).
- **Unfinished steps stay visible:** new drafts retain source-described actions such as washing while leaving disputed settings absent. A linked open method question marks the step **Needs clarification**, including in print. **Discuss with assistant** carries the selected question and the version being read. Recording a response or editing instructions does not resolve the question or permit final activation. This represents identified uncertainty; it does not automatically discover every missing scientific setting or rewrite earlier drafts.
- **Selected question in chat:** long questions have a compact preview and **Full question** disclosure. The complete question, SOP/status, response controls and stale-version safeguards remain available; collapsing the preview does not change scientific text or saved context.
- **Concise readiness:** the overview counts open method decisions by question ID, with **Resolve with assistant** and a folded choice of individual questions. Other blockers stay visible, and **All readiness checks** retains the complete checks. While blocked, **Review ready sections** names what it reviews and states that the SOP remains a draft; **Confirm SOP** is the separate final action when eligible. This first presentation slice does not add scientific decision approval or close the full reconciliation plan.
- **Benchmark**: per-section scores on the test set, run with any model pair, before and after review, reported in PR descriptions (built: `sops.score` and `pnpm --filter @ailab/api sop:benchmark` against the expectations in `seed/sop-benchmark`; so far the InterLab protocol from its LabOP model).
- **Editing** (built, [ADR 0046](../decisions/0046-sop-text-and-one-confirm.md)): one highlighted text box per value and per step's words. Values light up blue and materials orange as they are typed; what a value's text says decides its kind (a number, a formula, `Material.field`); a step's materials and settings are read from its words. Hover cards say how a value is worked out and where it came from; at the bench a number from a value keeps its color. Storage is unchanged. Edit opens the whole SOP as one form with one Save, and one Confirm (`records.confirm`) confirms every part that is ready. The assistant fills in a value, a step's settings, a step from a sentence or the steps from the source on request (`sops.suggest`), shown in agent ink until a person changes it.
- A confirmed SOP version is immutable. Experiments pin the version they use; a new version flags experiments still designing.
- Out: a printable and tablet view. Robot code is generated from transfer plans (016), not from SOPs.

**Scientific reconciliation ([004g](../plans/004g-ai-first-scientific-reconciliation.md), ADRs [0068](../decisions/0068-interactive-scientific-decisions.md)/[0069](../decisions/0069-working-methods-and-scientific-uncertainty.md)):** new draft fixtures use one typed question contract. `sops.ask_question` appends an open question; people-only `sops.answer_question` records a response or corrects wording while preserving history. An unknown response stays open. Generic writes and restore cannot rewrite questions. Initial experiment questions require a declared input or late-bound material; the pinned experiment and run calculation enforce that obligation. Method conflicts remain blockers. Run-stage deferral and broader scientific decision Apply remain pending beyond the bounded draft-volume backend above. Questions keep current library citations, with no immutable edition claim. Accepted SOPs refuse editing until the revision workflow lands, including working drafts with accepted history; raw history remains readable. Populated-lab migration/future-use acceptance remains SG-10c work, and immutable source reading remains SG-18. See the [current bounded contract](../architecture/sops.md#scientific-decisions-contract-foundation-004g--sg-01).

The bounded experiment-input acceptance path is paired on the unreleased branch for one existing open experiment/input question on a never-confirmed draft. It changes only that question's accepted deferral, preserving the method and section reviews; the input is still required for every experiment after separate SOP confirmation and pinning. Responses remain possible, accepted wording needs reconsideration, and deleting/converting the input is refused. The independent producer checkpoint cleared this scope. Public preparation uses a strict question selector alongside the unchanged volume selector and pauses assistant work. Sole person Apply uses the shown digest, refreshes changed meaning while pending, and commits an atomic durable receipt under held locks. Final integrated gates/review/browser acceptance remain pending before release. See the [bounded acceptance contract](../architecture/sops.md#existing-experiment-input-acceptance).
